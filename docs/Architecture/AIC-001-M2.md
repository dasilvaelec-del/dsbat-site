## C. Structure actuelle des pièces

```js
{
  id: 'chambre',            // identifiant de type (clé PIECES_DEF)
  nom: 'Chambre 2',         // libellé affiché (numéroté si quantité > 1)
  icon: '🛏️',
  numero: 2,                // rang de l'instance
  dims: { l, la, h, fenetres, portes },      // cotes saisies (défauts h=2.5, fenetres=1, portes=1)
  config: {                  // quantités par métier, par code de prestation
    electricite:{CODE:qty}, plomberie:{…}, vmc:{…}, peinture:{…}, carrelage:{…},
```

## J. Redondances / risques de double stockage

1. **`dsbat.projet` (ModeleProjetDSBAT) vs globales** : l'objet Projet est **reconstruit à la demande** depuis `{chantier, piecesSelectionnees, metiersActifs}` (pas de copie persistante) → **pas de duplication** aujourd'hui. **RISQUE si M2 crée un 2e objet** : il faut enrichir `dsbat.projet`, pas le cloner.
2. **Surface déclarée (`chantier.surface`) vs somme des surfaces des pièces** : **deux informations distinctes** (déclarée ≠ calculée) — à **conserver séparées** (le contrôle M1-B repose exactement sur cette distinction). ✅
3. **Gamme** : `chantier.qualiteMateriaux` (global) n'est qu'un **seed** ; la vérité est par pièce (`elecGamme/ploGamme/faienceFormat`). Ne pas réintroduire une gamme globale.
4. **VMC / chauffage** : présents à 3 endroits (chantier `vmc`/`chauffage`, métier coché, config par pièce) → le Contexte doit **référencer**, pas recopier.
5. **Coordonnées client** : saisies en amont **et** re-demandées par `captureModal` → à unifier via le Contexte (lecture), pas dupliquer.

**Principe retenu** : une seule **donnée source** par information ; le Contexte expose des **vues dérivées** (déduites/calculées/affichées) sans jamais créer une 2e vérité.

## K. Proposition de structure conceptuelle du Contexte Projet

Poser une **couche d'enrichissement** au-dessus du contrat `dsbat.projet` existant, en réutilisant ses emplacements réservés (`decisions`, `journaux`, `metadonnees`) et en ajoutant une vue dérivée **pure** :

```
projet (dsbat.projet — EXISTE déjà, inchangé)
├── identite, client, chantier, metiers, pieces, versions, reproductibilite   (source de vérité)
├── resultats            (devis/parPiece — déjà prévu)
│
└── contexte  (NOUVELLE VUE DÉRIVÉE, lecture seule — à créer)
    ├── declare        : { typeBien, typeLogement, surfaceTotale, metiersActifs, … }  ← recopie de référence
    ├── calcule        : { surfaceConfiguree, ecartSurfacePct, nbPiecesParType, … }
    ├── deduit         : { profilRenovation, profilLogistique, categorieAge, … }       (dérivés purs)
    ├── confirme       : { … }   (déductions validées par le client)
    ├── incoherences[] : ← verifierCoherenceGlobale (EXISTE)
    ├── recommandations[] : ← RecoEngine / oublis (EXISTE)
    ├── hypotheses[]   : propositions non confirmées (chauffage/ECS/VMC/extérieurs…)
    ├── aVerifierVisite[] : points « inconnu » / écarts (ex. tableau inconnu)
    └── confiance{}    : niveau par bloc, quand pertinent
```

- **Mapping demandé (§8) → réalité :** `projet.typeBien` = `chantier.typeBien` ; `projet.surfaceTotale` = `chantier.surface` ; `projet.typeLogement` = `chantier.typeLogement`/`pieces` (T-n) ; `projet.metiersActifs` = `metiersActifs` ; `projet.pieces` = `piecesSelectionnees` ; `projet.equipements` = dérivé des `config` + champs chantier (borneVE/pv/domotique) ; `projet.contexteQuestionnaire` = `chantier` ; `projet.contraintes` = `accessibilite`+`accessSup` ; `projet.informationsComplementaires` = `description` (**à re-transporter**, §M).
- **Règle d'or** : `contexte` est **calculé à la volée** (fonction pure), **jamais** réinjecté dans le prix/quantités. Le Runtime reste l'autorité de calcul.
