# AIC-001 — Audit fonctionnel complet du configurateur DSBAT

> **Document d'architecture fonctionnelle.** Base de référence pour l'évolution vers l'AIC (Assistant Intelligent de Configuration).
> **Nature : audit strict.** Aucune modification de code, aucun patch, aucune suppression de question, aucun déplacement d'étape n'a été effectué ni n'est proposé ici. Ce document décrit **l'existant tel qu'il est**.

---

## 0. Périmètre, méthode et avertissement

**Périmètre réel du parcours.** Contrairement à ce que suggère la vision en 7 étapes, le configurateur DSBAT est réparti sur **deux pages distinctes** reliées par le `sessionStorage` du navigateur :

| Page | Rôle | Étapes de la mission couvertes |
|------|------|-------------------------------|
| `devis.html` | Assistant amont en 4 étapes (wizard) | Vos informations · Chantier · Travaux |
| `devis-configurateur.html` | Configurateur en 3 phases | Configurateur par pièce · Configuration des corps de métier · Récapitulatif · Génération du devis |

Le pont entre les deux : à la fin de `devis.html`, `envoyerDevis()` écrit trois clés (`chantier`, `client`, `devisMetiers`) dans `sessionStorage`, puis redirige vers `devis-configurateur.html` qui les relit au chargement.

**Méthode.** Lecture directe du code source des deux pages et des moteurs (`js/moteur-devis.js`, `js/moteur-piece*.js`, `js/moteur-revetements.js`, `js/coherence.js`, `js/moteur-recommandations.js`, `js/moteur-tva.js`, `js/parametres-metier.js`, `runtime/moteur-prive/prix.js`). Chaque règle citée a été **observée dans le code**, jamais supposée. Là où une règle vit dans un moteur privé non lu ligne à ligne, le document nomme le module responsable sans en inventer le détail.

**Légende d'importance** (classement, pas une recommandation de suppression) :
🟢 indispensable · 🔵 probablement déductible · 🟠 pourrait devenir une confirmation · ⚪ uniquement informative · ❓ utilité non identifiée

⚠️ **Aucune question ne doit être supprimée.** Le classement ci-dessous sert uniquement à préparer la réflexion AIC.

## 1. Vue d'ensemble du parcours

```
PAGE 1 — devis.html (wizard 4 étapes)
  Étape 1 : Vos coordonnées + source + délai + type de demande
  Étape 2 : Caractéristiques du chantier (projet, dimensions, accès, installations, qualité)
  Étape 3 : Corps de métier souhaités + description libre
  Étape 4 : Récapitulatif → envoyerDevis()
            │
            ├─ sessionStorage['chantier'] = {…19 champs}
            ├─ sessionStorage['client']   = {nom, tel, email, adresse, source, delai}
            ├─ sessionStorage['devisMetiers'] = [métiers cochés]
            ├─ Lead e-mail (FormSubmit → contact@dsbat.fr) + ouverture WhatsApp
            └─ redirection ↓

PAGE 2 — devis-configurateur.html (3 phases)
  Phase 1 : Objectif du projet + sélection des pièces + dimensions par pièce
  Phase 2 : Configuration pièce par pièce, corps de métier par corps de métier
  Phase 3 : Écran de capture des coordonnées → Récapitulatif → PDF / Runtime
```

**Observation structurante n°1.** Les coordonnées client sont demandées **deux fois** : une fois en Étape 1 de `devis.html` (obligatoire), une seconde fois via la modale `captureModal` avant l'affichage du récapitulatif du configurateur. (Voir diagnostic §5, question 1.)

**Observation structurante n°2.** Les données « chantier » (surface globale, nombre de pièces, typologie) servent à **proposer** une composition de pièces dans le configurateur, mais les **cotes réelles** sont re-saisies pièce par pièce. Les deux niveaux coexistent volontairement (le concepteur a documenté ce choix : « ce sont vos cotes qui font le calcul, jamais des valeurs par défaut »).

## 2. Modèle de données

**`client{}`** (sessionStorage `client`) : `nom`, `tel`, `email`, `adresse`, `source`, `delai`.

**`chantier{}`** (sessionStorage `chantier`) : `codePostal`, `ville`, `typeBien`, `typeLogement`, `etage`, `ascenseur`, `surface`, `pieces`, `ageBati`, `etatLieux`, `typeProjet`, `hauteurPlafond`, `accessibilite`, `accessSup`, `qualiteMateriaux`, `chauffage`, `vmc`, `eauChaude`, `tableauExistant`, `borneVE`, `pv`, `domotique`.

**`metiersActifs[]`** (sessionStorage `devisMetiers`) : sous-ensemble de `['electricite','plomberie','vmc','isolation','peinture','menuiserie','sols','carrelage']`.

**`piecesSelectionnees[]`** — chaque pièce :
```
{ id, nom, icon, numero,
  dims:   { l, la, h, fenetres, portes },
  config: { electricite:{CODE:qty}, plomberie:{…}, vmc:{…}, peinture:{…}, carrelage:{…}, menuiserie:{…}, peinture_auto:montant },
  elecMethode, elecGamme, ploGamme,
  peintMur, peintPlaf, peintPapier,
  solMateriau, solSousCouche,
  faienceMode, faienceHauteur, faienceFormat, faienceSurface,
  normeMin, _recoApplique, _oublisIgnores…,
  surfaces:{sol,murs,plafond}, totalHT, tempsChantier }
```

**Persistance.** `sessionStorage['configEtatV1']` (compteurs, dimensions par instance, pièces, objectif) — un rafraîchissement ne perd pas la saisie.

## 5. Analyse générale (diagnostic)

> Diagnostic uniquement. Aucune correction n'est proposée.

**1. Le configurateur pose-t-il plusieurs fois la même information ?**
Oui, à plusieurs endroits :
- **Coordonnées client** demandées deux fois (Étape A obligatoire, puis modale `captureModal` en phase 3).
- **Dimensions** : surface globale (B6) + nombre de pièces (B7) en amont, puis **cotes réelles par pièce** (D2) dans le configurateur. Les premières servent à *proposer* la typologie, les secondes à *calculer* — coexistence assumée mais redondante du point de vue client.
- **Niveau/gamme** exprimé trois fois selon des axes différents : « Gamme de matériaux » (B17), « Objectif du projet » (D0), et les gammes fines par pièce (E2 élec, E4 plomberie, E8 faïence).
- **VMC** : présence existante (B15) + métier VMC coché (C1) + configuration VMC par pièce (E9). **Chauffage** : type (B14) recoupé par la configuration électrique.

**2. Certaines informations semblent-elles ne jamais être utilisées ?**
Oui, non relues par les moteurs dans le code observé : **Étage (B4)**, **Ascenseur (B5)**, **Panneaux solaires (B20)**, **Ville (A6)** (le calcul passe par le code postal), **Domotique (B18)** (lecture unique, sans règle de chiffrage). **Source (A7)** et **Délai (A8)** sont commerciaux, non calculatoires (usage légitime hors moteur).

**3. Certaines règles métier semblent-elles incomplètes ?**
- **Lecture morte** : un moteur lit `chantier.statut`, or le champ est stocké sous `chantier.typeLogement` → la valeur lue est toujours `undefined`. Règle vraisemblablement inaboutie.
- **Domotique / Panneaux solaires / Étage / Ascenseur** : collectés mais sans règle de chiffrage — intentions non finalisées côté moteur.
- **Hauteur sous plafond (B8)** : saisie globalement puis re-déterminée par pièce (`dims.h`) — la valeur globale n'a pas d'effet tarifaire clair.

**4. Certaines questions paraissent-elles très importantes pour le moteur mais peu mises en valeur dans l'interface ?**
- **Code postal (A5)** : détermine le **coefficient de zone sur tout le devis**, mais présenté comme un simple champ d'adresse, sans signaler son poids tarifaire.
- **Tableau électrique actuel (B13)** : décide de chiffrer (ou non) un poste majeur + le parafoudre, présenté comme une simple info d'installation.
- **Contraintes particulières → « Logement occupé » (B12)** : applique une **majoration de +8,8 %** sur tout le total, sans que l'ampleur soit visible.
- **Configuration électrique par pièce (E3)** : pilote silencieusement le dimensionnement du tableau — un poste souvent conséquent.

**5. Certaines parties du configurateur risquent-elles de perturber le client ?**
- La **re-demande des coordonnées** en fin de parcours (F1) peut être perçue comme un doublon frustrant.
- La **densité de l'Étape 2** (B : ~20 champs sur une page) peut décourager, d'autant que plusieurs champs n'ont pas d'effet visible sur le prix.
- Le **double niveau dimensions** (surface globale puis cotes par pièce) peut sembler contradictoire (« pourquoi redemander ? »).
- La **coexistence de trois axes de gamme** (B17 / D0 / gammes par pièce) peut créer une impression d'incohérence ou de sur-questionnement.

**6. Quelles sont les dépendances les plus critiques du moteur ?**
Par ordre d'impact :
1. **Code postal → coefZone** (multiplie le total entier).
2. **Configuration électrique par pièce → Tableau NF C 15-100** (couplage le plus riche du moteur).
3. **Dimensions par pièce → surfaces → tous les revêtements** (peinture, sols, carrelage, faïence).
4. **Type de projet → sous-couche peinture + recommandations + cohérence**.
5. **Accessibilité / contraintes → forfaits + majoration** (postes additifs et multiplicatif).
6. **Chauffage / VMC / eau chaude / borne VE → circuits du tableau**.
7. **metiersActifs → périmètre entier** des sections et moteurs.

Le configurateur actuel est un **moteur riche et cohérent** : la majorité des champs alimente réellement le calcul, avec des couplages forts (élec↔tableau, chauffage↔tableau, isolation↔peinture, dimensions↔revêtements) qui constituent le « savoir d'artisan » déjà encodé. Trois axes ressortent pour la réflexion AIC, **sans rien supprimer** :

1. **Déduction** : plusieurs champs pourraient devenir des *confirmations* déductibles (typologie ↔ pièces réelles, hauteur globale ↔ cotes, VMC existante ↔ métier VMC, gamme globale ↔ gammes par pièce).
2. **Hiérarchisation** : quelques questions à fort impact tarifaire (code postal, tableau existant, logement occupé, config élec) gagneraient à être mieux signalées ; d'autres sans effet moteur (étage, ascenseur, PV, domotique) sont candidates à un rôle purement qualificatif.
3. **Nettoyage de règles inabouties** : la lecture `chantier.statut` (vs `typeLogement`) et les champs collectés-mais-non-exploités matérialisent des intentions à finaliser ou à assumer comme informatives.

Ce document fige la photographie fonctionnelle du « cerveau » actuel. Toute évolution AIC pourra désormais être pensée **par rapport à cette cartographie**, en préservant les dépendances critiques identifiées au §4.3.
